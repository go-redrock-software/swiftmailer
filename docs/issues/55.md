# Issues #55 / #56 / #57: Isolate Gmail SDK request policy

**Branch:** fix/55-isolate-gmail-sdk-requests
**Base / review target:** !17 / fix/53-disable-http-api-redirects (`78a74334`)

**Issues:** https://code.go-redrock.com/trac/swiftmailer/-/issues/55 (confidential report) , https://code.go-redrock.com/trac/swiftmailer/-/issues/56 and https://code.go-redrock.com/trac/swiftmailer/-/issues/57

## Design

### Approach
Use `fix/55-isolate-gmail-sdk-requests` based on !17 (`78a74334`). Keep Gmail's real SDK request construction, authentication, retry runner and response decoding, but execute through a transport-local SDK copy and a scoped Guzzle-compatible redirect guard. Preserve caller-owned SDK/HTTP configuration and handler stack; share the SDK token cache so authentication behavior persists across sends. Also fix the confirmed deferred-request false-success mode (#56).

### Changes
- A small ClientInterface decorator forces per-request redirect refusal, rejects 3xx responses with the existing non-retryable marker and exposes a cloned handler configuration to SDK authentication (which creates its own Guzzle clients). Place request policy before redirect middleware and response validation before SDK retry decoding. Delegate ordinary errors and async behavior normally.
- Gmail send creates a scoped copy of the supplied standard Google Client, uses the shared cache and guarded HTTP client, and forces immediate execution on the copy. Caller defer/client/defaults/handler stack remain unchanged. Fail clearly for non-cloneable or non-cooperating SDK customizations; reject any returned deferred request instead of counting it as sent.
- Preserve the existing zero-return behavior for ordinary SDK exceptions while letting the non-retryable marker propagate through the SDK send-event cleanup path.
- Real SDK/auth/redirect tests cover redirect statuses/destinations, fresh/expired credentials, token-cache/callback behavior, retry settings, successful and error decoding, caller state, deferred mode, MIME/attachments, explicit envelope policies and failure cleanup. All fixtures use fabricated credentials.
- Register the new helper in metadata/runtime aliases without importing the independent #51 generator change. Update release/API/security documentation and shared docs/issues/55.md.
- Assess SES and Graph SDK boundaries independently with installed-source review and no-provider probes; record concrete separate findings instead of claiming blanket SDK protection.

### Acceptance Criteria
- Failing-before/fixed-after public-send evidence for Gmail redirects and deferred false success, using real middleware and no real provider email/tokens.
- One Gmail request on a redirect and no automatic replay, including default Swift retries and SDK retry configuration. A separate necessary token exchange may occur; token-exchange redirects must also fail closed.
- Caller SDK HTTP client identity, defer mode, client options and handler stack stay intact; SDK callbacks and shared token cache retain ordinary behavior across sends.
- Normal SDK success/error decoding, MIME/Bcc/attachment fidelity, policy/envelope cleanup and existing count behavior remain covered. No direct-HTTP regressions from !17.
- Helper sync/async paths and SDK-created client configurations are tested. Unsupported SDK customization fails before sending rather than bypassing the guard.
- Full PHP 8.3/8.5 suites, PHPStan, full style, strict Composer validation and final-head required CI pass. No baseline/profile/threshold changes or merge.

### Risks
SDK cloning is required for isolated configuration; the standard Google Client supports it. User subclasses must honor SDK cloning and HTTP configuration setters. Authentication uses the same cache/credential objects and callbacks, but request configuration is isolated. The SDK's own middleware/client creation must retain the policy, so simple outer wrappers alone are insufficient. Other SDK transports have distinct interfaces and ownership boundaries. The unmerged API stack and optional CI prerequisites #38/#40/#45/#46 remain pending review/integration.

## Implementation

### Changes and approach
- Added `Swift_Transport_Api_NoRedirectClient`, with all four Guzzle sync/async entry points guarded through an isolated client/handler configuration, including SDK-created authentication clients. Request policy runs before redirects; response rejection runs before SDK retry decoding. A redirect latches the operation to prevent another request through the same scope. A real caller retry-middleware check exposed four failing direct paths before this final adjustment; both authenticated and no-auth SDK paths now reject before caller retry handling, while ordinary 503 retries remain functional.
- Gmail uses a cloneable local SDK copy with immediate execution, preserving the original HTTP client, handler stack, options and deferred mode. Initializes and shares the SDK cache; normal default/custom token callbacks remain active, including the default callback's updates to the original SDK token. Unsupported clone/setter/deferred-result customizations fail with the non-retryable marker. Ordinary SDK errors retain zero-return cleanup.
- Removed the duplicate attachment loop from `Swift\getRawMessage()`. `toString()` already contains the complete MIME tree; reappending children corrupted the MIME epilogue (#57).
- Added 152 regression cases across real Google SDK/Guzzle middleware and direct helper tests: all five redirect statuses, four destination types, explicit envelopes, caller deferral, fresh/refresh/service-account authentication, callbacks/cache across sends, normal SDK retry/error behavior, policy cleanup, unsupported SDK customizations, all sync/async/config-derived HTTP paths and repeated binary/stream/inline/multipart MIME sends. Multipart comparison normalizes only transient generated boundary names; exact serialized MIME and epilogue checks otherwise remain.
- Updated class metadata/runtime alias and release/API/security documentation. No unrelated #51 generator changes, vendor changes, baselines or mutation thresholds.

### Evidence and verification
- Before implementation: 82 new public-send cases failed; caller-deferred probe reported one accepted recipient with zero wire requests. Initial guard fixed redirects but two exact MIME comparisons exposed #57; removing duplicate export fixed those controls.
- Final focused tests: 165 tests / 1,803 assertions, including existing Google transport cases. Full suites: PHP 8.5 — 6,689 tests / 56,777 assertions / 30 skips; PHP 8.3 — 6,689 tests / 56,779 assertions / the two known E_ERROR expectation warnings / 30 skips. Final-head CI results are recorded in the MR readiness note.
- PHPStan, full style (511 files), strict Composer validation and whitespace checks pass.
- All Google fixtures use fabricated tokens and canned HTTP responses. Service-account tests generate an ephemeral local signing key; no provider request or email is sent.

### Independent SDK assessment
- Confidential #58: Microsoft Graph 2.56.0 / kiota-http-guzzle 1.5.2, real GraphRequestAdapter + Guzzle middleware + MockHandler, 307 then 202. Public send reported two recipients; both original Graph and redirected cross-origin requests contained the serialized body and Bcc. Anonymous authentication was used, so no OAuth header claim is made.
- Confidential #59: AsyncAws core 1.30.0 / SES 1.17.0, both SES transports with default SDK HTTP stack, explicit fake credentials and two ephemeral loopback servers. A 307 forwarded body/Bcc to the second port; both sends reported two recipients. Authorization was stripped on the second hop. Servers were shut down; no AWS endpoint was contacted.
- These are separate design tasks. This MR makes no blanket claim that all SDK transports refuse redirects.
- SDK integration was checked against installed sources and current primary documentation: [Google client](https://github.com/googleapis/google-api-php-client), [Guzzle handlers](https://docs.guzzlephp.org/en/stable/handlers-and-middleware.html), [Graph custom clients](https://github.com/microsoftgraph/msgraph-sdk-php/blob/main/docs/authentication_samples.md), [AsyncAws configuration](https://async-aws.com/configuration.html). Context7 was used first; its AsyncAws results omitted core/SES, so Firecrawl retrieved the official configuration page.

### Review notes
- Review the cloned handler's ordering and retained policy in Google's derived auth clients, as well as SDK clone/callback ownership. The helper is scoped to one operation, not a reusable general-purpose HTTP client.
- Standard Google Client behavior is supported. Injected HTTP clients must expose a full Guzzle-compatible configuration and callable handler. The transport creates a Guzzle client from that configuration, as Google authentication itself does; custom overrides of an injected HTTP client's send/request methods are not copied. Arbitrary SDK subclasses/handlers must honor SDK/Guzzle contracts; the runtime checks cover non-cloneable clients and ignored HTTP/defer setters, not malicious overrides.
- Stacked on !17. Optional CI bootstrap/target-ref/deprecation prerequisites remain tracked separately in #38/#40/#45/#46. No merge is authorized here.
