# Issue #33: Escape recipient addresses in HTML delivery reports

**Branch:** fix/33-escape-recipient-addresses-in-html-delive
**MR:** https://code.go-redrock.com/trac/swiftmailer/-/merge_requests/1
**Issue:** https://code.go-redrock.com/trac/swiftmailer/-/issues/33

## Design

## Implementation Plan

### Approach
Escape HtmlReporter recipient text once before either output branch using htmlspecialchars with ENT_QUOTES | ENT_SUBSTITUTE and explicit UTF-8. Retain normal entity escaping so literal entity-like addresses remain literal text. Keep the reporter interface, report markup, status, and message untouched.

### Changes
- lib/classes/Swift/Plugins/Reporters/HtmlReporter.php
- Reporter regression tests for direct notifications and ReporterPlugin send events using real validated messages.
- doc/security.md, CHANGES, and docs/issues/33.md.

### Acceptance Criteria
- Both success and failure results display HTML payloads as text.
- Quotes, ampersands, entity-like input and valid Unicode are preserved safely; malformed UTF-8 uses replacement characters.
- Valid quoted recipient payloads in To, Cc and Bcc cannot introduce elements through ReporterPlugin.
- Regression tests fail before the fix and pass afterward; run the full test suite and relevant quality checks.

### Risks
Applications relying on raw HTML embedded in an address will see escaped text. This is intentional security hardening of a plain recipient field. Escaping applies to the reporter only.

## Implementation

### Changes
- HtmlReporter now escapes recipient text once before rendering either result.
- Added 16 cases for markup, quote and ampersand escaping, literal entities, Unicode, malformed UTF-8, and real validated To/Cc/Bcc recipients passed through ReporterPlugin.
- Updated CHANGES and both plugin/security guides to describe the vulnerability and corrected behavior.
