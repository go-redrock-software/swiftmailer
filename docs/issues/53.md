## Design

### Approach
Use `fix/53-disable-http-api-redirects` based on !16 (`4ccd34c9`). Disable automatic redirects in the options of every Swift-owned direct HTTP API request, including all provider sends and health checks. A per-request setting must override injected Guzzle client defaults without mutating caller-owned clients. Preserve the existing #50 response-boundary/non-retryable failure lifecycle.

### Changes
- Add `allow_redirects=false` to 20 direct request sites: 17 sends, shared GET ping, Mandrill POST ping and Azure HMAC GET ping. Infobip's shared options cover normal multipart and explicit-envelope JSON delivery.
- Correct Azure ping's false-positive status rule (#54): retain successful 2xx and its expected authenticated 404, reject redirects and other client/server errors.
- Real Guzzle MockHandler/HandlerStack/history regression matrix covering all five redirect statuses, cross-origin HTTPS, HTTP downgrade, same-origin relative and loopback destinations. Verify no second request with injected redirect-enabled defaults, normal/matching envelopes, retry wrapper and recipient policies.
- Check all 17 provider sends and all ping implementations, with positive success controls and Azure acknowledgement/error controls. Assert failure events, effective recipients, cleanup and unchanged caller client defaults.
- Audit SDK-backed SES/Gmail/Graph boundaries separately; document delegation and any distinct findings without silently altering caller-owned SDK configuration or claiming unverified SDK protection.
- Add release/API/security documentation and a shared `docs/issues/53.md` handoff. Keep detailed reproduction in confidential #53; the internal-repository MR documents the request-destination rule and test evidence.

### Acceptance Criteria
- Establish failing-before public-send/ping evidence using real redirect middleware, no network or provider credentials.
- All direct request paths refuse redirects at the first response, including injected clients that enable redirects and HTTP-to-loopback/downgrade targets.
- Redirect send failures dispatch normal failure/completion, report effective recipients, restore policies/envelopes and do not replay under the default retry classifier.
- Valid provider acknowledgements/diagnostics remain supported; all health checks reject redirects, and Azure's 2xx/404 controls pass while other error statuses fail.
- SDK ownership boundaries and any follow-up risks are explicit. No blanket claim covering arbitrary SDK clients.
- Focused/full PHP 8.3/8.5 tests, PHPStan, full style, strict Composer validation and all final-head required CI pass. No mutation/deprecation baseline or threshold changes, live email or merge.

### Risks
Automatic redirects become an explicit transport failure even for a same-origin endpoint relocation; configure the correct endpoint instead. One request per send/ping is required to preserve credentials, message destination and delivery certainty. Custom client implementations must respect Guzzle request options. The API stack remains unmerged and optional CI prerequisites #38/#40/#45/#46 remain pending !11 integration.
