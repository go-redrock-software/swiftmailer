## Design

Audit all 21 concrete API transports. Preserve visible headers independently of delivery addresses where the provider supports raw MIME/envelope fields. Implement supported overrides and reject unsupported overrides before any provider delivery request. Keep counts consistent with submitted payloads. Ensure SDK transports dispatch recipient-policy events with the effective envelope, restore modified messages and report failures.

Verify current official provider contracts. Cover differing header/envelope recipients and senders, blind recipients, immutable caller input, rejection and cleanup, and counts. Run PHP 8.3/8.5 suites and quality checks.

## Provider audit

The full sourced matrix is in [API transports](../../doc/api-transports.md#explicit-envelopes), checked on 2026-10-15 using Context7 and official provider pages (Firecrawl fallback where no relevant Context7 library was available).

- Postal: raw MIME, separate mail_from and rcpt_to.
- Mandrill: messages/send-raw.json with raw_message, from_email and to. Tags/metadata use documented SMTP control headers; comma-containing tags are rejected.
- Mailgun: messages.mime file upload with independent to; independent sender rejected.
- Infobip: email/4/mime with base64 mimeMessage and destinations; From remains in MIME, independent sender rejected.
- Both SES variants: Raw content, explicit Destination, sender mapped to FeedbackForwardingEmailAddress. AWS controls wire MAIL FROM; this is bounce/complaint forwarding, not arbitrary SMTP MAIL FROM.
- Gmail and Graph: matching mail envelopes only. Graph sets From explicitly for these sends, subject to provider permissions. Explicit envelopes with Graph calendar conversion are rejected before SDK operations.
- Remaining 13 HTTP implementations accept matching envelopes and reject unsupported overrides before any delivery request. This describes implemented endpoints, without claiming providers have no other capabilities.

Raw payload copies strip Bcc, Resent-Bcc and internal X-Mailer control headers; visible headers, Message-ID, attachments and original caller Bcc remain intact. Raw paths submit unique recipients. Gmail requires Bcc in its API MIME input to deliver it and uses provider handling; Graph uses a dedicated Bcc field.

## Implementation

### Changes

All 21 concrete transports; shared validation, raw MIME copy and SDK send-event helper in AbstractApiTransport; accurate nullable address-getter PHPDocs; ApiEnvelopeTest integration coverage; three legacy transport tests and the recipient-policy integration fixture; API/sending guides and CHANGES.

### Approach

Apply validation to the effective envelope after recipient policies run. Use raw paths only with an explicit envelope, preserving legacy payloads otherwise. SDK sends now expose the envelope to plugins and run sendPerformed in finally. This fixes previously absent SES recipient-policy enforcement and missing Gmail/Graph envelope events. Correct SES recipient counts, Graph Reply-To counts and SES empty-provider-ID success reporting.

The failure-path review found the SES HTTP wrapper appending header recipients even when a different envelope was attempted. A regression reproduced that error; failure recording now belongs to the shared helper and reports only the attempted audience.

### Validation

- 66 new integration scenarios cover provider matching/rejection paths, raw payloads, deduplication, caller immutability, Bcc privacy, recipient policies, SDK failure cleanup and zero-result handling.
- Full PHP 8.5 suite: 4,305 tests, 26,046 assertions, 30 service-dependent skips; exit 0 with the standard project deprecation policy.
- Full PHP 8.3 suite: 4,305 tests, 26,044 assertions, 30 service-dependent skips; exit 0, with two existing PHPUnit E_ERROR expectation warnings.
- PHPStan: no errors; no baseline expansion.
- Full formatter dry run: 0 of 501 files need changes; Composer strict validation and git diff checks pass.
- Provider requests were mocked. No live provider mail, calendar invitations or credentials were used. These checks validate outgoing contracts, not delivery/account permissions.
