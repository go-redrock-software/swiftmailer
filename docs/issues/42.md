## Design

Apply allowlist/catch-all/redirect policy to actual ICS attendee audiences in listener order without nested send events. Use policy-adjusted invite keys. Preflight existing-event audiences before update/cancel, rejecting unknown or unsafe notification audiences. Preserve supported calendar lifecycle behavior, caller restoration and failure cleanup. Count actual notification/mail submissions instead of unsent mail headers.

Verify current Graph contracts and exercise full SDK payloads and lifecycle against an in-memory mailbox. Run PHP 8.3/8.5 suites, PHPStan and formatting. No live invitations or provider credentials are used.

## Implementation

### Changes

- SendEvent supports named transport audiences and reusable filters in listener order. Additional audiences can be discovered after beforeSendPerformed without re-entering listeners. Recording a verified delivery decision does not apply filters again.
- AllowlistPlugin and RedirectingPlugin register corresponding additional-audience policies. A permitted calendar audience is not rejected just because mail headers were filtered out.
- Graph re-reads ICS parts after listeners, filters attendees, retains names/roles, deduplicates delivery addresses, and uses the adjusted audience in invite keys. Fully removed audiences are skipped without forwarding the ICS as fallback.
- All invite lookups and current-audience reads finish before the first mutation. Existing audiences must be known; active policy rejects non-single-instance events and any stored audience that the policy would change. It never tries to repair an unsafe audience by PATCHing attendees away, because that can notify them.
- Counts exclude unsent mail headers and Reply-To. Update notifications account for old and new attendees; cancellation uses stored attendees. Failure metadata uses effective calendar/mail audiences, with completion/restore in finally.
- Updated event/API/Graph guides and CHANGES, including previously stale UID/transactionId and count documentation.

### Provider contracts

Checked on 2026-10-15 with Context7 and official Microsoft pages:

- [Update event](https://learn.microsoft.com/en-us/graph/api/event-update?view=graph-rest-1.0): attendee changes and removals can generate meeting updates; recurring masters can notify separately edited instances.
- [Cancel event](https://learn.microsoft.com/en-us/graph/api/event-cancel?view=graph-rest-1.0): operates on the existing event rather than accepting a replacement recipient list.
- [Get event](https://learn.microsoft.com/en-us/graph/api/event-get?view=graph-rest-1.0): retrieves attendees/type for the preflight inspection.
- Further discovery: [Microsoft's Teams Graph endpoint reference](https://learn.microsoft.com/en-us/javascript/api/teams-sdk-typescript/@microsoft/teams.graph-endpoints/users.events?view=msteams-sdk-ts-latest) exposes an optional If-Match parameter for DELETE event, while its PATCH event parameters omit it. Investigate conditional DELETE as the supported cancellation route, verifying organizer-only behavior, an available event ETag and stale-version rejection. Do not assume this establishes conditional PATCH or POST cancel support. This is an actionable path for the remaining gate, not a completed implementation or live-provider verification.

## Review

### Findings

**Unresolved concurrency gate:** preflight reads and Graph mutations are not atomic. Another actor can change an event's attendees after the check. The fetched update/cancel contracts do not establish an If-Match guarantee. The code does not send an undocumented conditional header or claim atomic enforcement. Before #42 is closed, verify a supported conditional operation (including stale-version rejection) or make the unsupported existing-event path fail safely under recipient policy. The tested create/filter/key-isolation and preflight improvements are concrete progress, but this remaining requirement prevents a completed-security-fix claim.

**Separate default-dispatcher bypass:** the API base class silently discards registerPlugin calls when no dispatcher was injected. This is reproduced and tracked in [#44](https://code.go-redrock.com/trac/swiftmailer/-/issues/44); the current tests supply a real dispatcher. Do not infer coverage of default-constructor policy registration from these results.

Counts are submission/current-audience estimates, not final delivery receipts. Multi-request sends can partially succeed on provider failures; preflight prevents known unsafe later audiences from allowing earlier writes, but is not a transaction for external errors or edits.

### Verdict

Draft / changes required before merge: resolve the concurrency gate. External review pending.
