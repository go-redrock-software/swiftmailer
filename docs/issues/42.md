## Design

Apply allowlist/catch-all/redirect policy to actual ICS attendee audiences in listener order without nested send events. Use policy-adjusted invite keys, preserve names/roles, restore caller state, and count only submitted notification/mail audiences. Preflight all operations before the first write. Protect existing-event notifications from attendee changes; reject operations when the implemented provider path cannot enforce the policy exactly.

Build on #44's default listener registration and #39's SDK lifecycle. Use current official provider contracts and full SDK requests against an in-memory mailbox. Run PHP 8.3/8.5 suites, PHPStan, full formatting and Composer validation. No live invitations or credentials are used.

## Implementation

### Audience handling

- SendEvent provides named recipient groups and reusable filters in listener order. Both built-in recipient plugins register additional-audience policies while retaining mail-header/envelope behavior. No nested event dispatch corrupts plugin state.
- Graph exposes original ICS audiences before listeners, re-parses afterward, and applies all registered filters once. Allowed calendar recipients can proceed even if mail headers were filtered out. Retained attendees keep names/roles; new targets are required attendees. Removed ICS audiences are never forwarded as fallback attachments.
- Invite keys use policy-adjusted recipients, so redirected lookup never deliberately targets the production audience. Known unsafe, unknown or recurring stored audiences are rejected before notification.
- Ordinary mail is counted/submitted only when it has recipients. Send-alongside and attachments do not cause empty sendMail requests after header filtering. Failure metadata uses effective calendar/mail audiences, including when no external dispatcher exists.

### Concurrency resolution and provider limits

- Under active recipient policy, cancellation reads the stored attendees, type, organizer status and exact @odata.etag. The audience must be unchanged by policy, the event must be a single instance, and isOrganizer must explicitly be true.
- Cancellation uses organizer-side DELETE with If-Match carrying the exact stored tag, rather than an unconditional cancel action. Missing, malformed, wildcard or multiple tags are rejected. Stale-version HTTP 412 propagates without re-fetch/replay or unconditional fallback.
- Existing-event REQUEST updates are rejected before write while recipient policy is active. The current verified endpoint contracts do not establish conditional PATCH for this implementation; silently accepting that race is unsafe. Create and conditional cancel remain supported. Without recipient policy, existing update/action-cancel behavior remains supported.
- Swift_Transport_NonRetryableException marks policy/version failures. The default retry classifier checks the entire cause chain before transient codes/messages, preventing both zero-code policy failures and wrapped HTTP 412 from being replayed. Custom classifiers remain caller-controlled.
- All plans are preflighted before the first write. This is not an all-or-nothing transaction for multiple provider operations: later network/provider failures can still follow earlier successful operations. Counts are submission/current-audience estimates, not delivery receipts.

### Provider contracts

Checked on 2026-10-15 using Context7 and official Microsoft documentation:

- [Delete event](https://learn.microsoft.com/en-us/graph/api/event-delete?view=graph-rest-1.0): deleting an organizer's meeting sends attendees cancellation notices.
- [Official Teams Graph event endpoint reference](https://learn.microsoft.com/en-us/javascript/api/teams-sdk-typescript/@microsoft/teams.graph-endpoints/users.events?view=msteams-sdk-ts-latest): DELETE event exposes an If-Match parameter; PATCH parameters omit it.
- [Get event](https://learn.microsoft.com/en-us/graph/api/event-get?view=graph-rest-1.0): response examples include @odata.etag metadata; the SDK preserves it.
- [Event resource](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0): isOrganizer identifies organizer ownership.
- [Update event](https://learn.microsoft.com/en-us/graph/api/event-update?view=graph-rest-1.0) and [cancel event](https://learn.microsoft.com/en-us/graph/api/event-cancel?view=graph-rest-1.0): describe notification side effects; no unverified conditional PATCH/action-cancel assumption is used.
