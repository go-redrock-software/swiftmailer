## Design

## Implementation Plan

### Approach
Add automatic failed-backend recovery to round-robin and failover pools, based on !25. Use a non-negative integer cooldown in seconds (default 60), configurable through constructors, runtime accessors and wrapper-level `?retry_period=N`. Preserve hard terminal failures and configured backend ownership from !24/!25.

### Changes
- Add optional `int $retryPeriod = 60` to low-level pool constructors and append it after the existing transports argument on convenience classes. Add `getRetryPeriod()` and fluent `setRetryPeriod()` with validation.
- Store failure times by backend object identity. Use a monotonic protected clock and recover due backend slots once at entry to send/ping/start. Preserve intentional weights; quarantine all slots for the same failed backend identity. Reset timing metadata on setTransports().
- Keep attempts bounded by the operation’s initial eligible pool. Period zero permits immediate eligibility on a later operation without an infinite same-message loop. A repeated failure starts a fresh cooldown. Sticky failover continues on its healthy current backend until it fails.
- Make start() respect cooldown so Swift_Mailer and RetryTransport automatic startup cannot bypass it. Document the behavior change from manual immediate resurrection; explicit period zero or pool reconfiguration provides immediate eligibility.
- Extend pool wrapper parsing with strict retry_period validation before constructing inner transports. Reject malformed, duplicate, unknown and overflowing wrapper options without exposing the credential-bearing DSN. Preserve inner retries/retry_delay and outer retry(...) combinations; retain existing flat-group nesting limits.
- Preserve function query metadata in Swift_Dsn_Configuration via getParameters()/getParameter(). It remains a metadata parser for its existing flat configurations; runtime validation and construction use DsnTransportFactory.
- Add failing-before public, clock-controlled behavior tests, factory/metadata tests and documentation. Adapt existing tests specifically about immediate manual restoration to request period zero, retaining their original assertions.

### Acceptance Criteria
- Default/custom/zero periods on both low-level and convenience APIs; invalid periods fail without changing existing settings. Due recovery at the exact deadline, not before, across partial/all-backend failures, false ping, send/start errors and changed runtime periods.
- No sleep during cooldown; no backend traffic before eligibility through direct sends, Swift_Mailer or RetryTransport. No repeated recovery within one operation, including zero period and weighted references. Recovery retains multiplicity, plugin bindings, explicit envelopes/events and caller-owned client/dispatcher identities.
- Preserve terminal causes without quarantine/replay, sticky failover, healthy rotation, reentrant pool replacement and correct cleanup ownership, including callbacks that rotate or restore the same configured pool. Clear stale failure metadata on replacement.
- Factory accepts `roundrobin(...)?retry_period=15` and `failover(...)?retry_period=0`, with valid retry combinations and unchanged inner DSN parameters. Strict numeric/range/duplicate/array/unknown/trailing-garbage cases fail before inner construction. Metadata helpers expose wrapper parameters separately from leaf parameters.
- Full PHP 8.3/8.5 suites, PHPStan, style, Composer/map/alias/diff checks and six required CI jobs at the exact final MR head. No dependency/vendor/baseline/threshold changes. No merge.

### Sources and Risks
The 60-second reference/default and wrapper syntax are documented in Symfony 7.4 and PR #54939 (linked on the issues). Context7 did not index Nyholm DSN after two resolution attempts; official Nyholm 2.0.1 README and installed source confirm DsnFunction query metadata. No dependency upgrade is included.

Default automatic recovery and cooldown-aware start() are deliberate behavior changes that require migration notes. Zero-period recovery must remain bounded. Backend identity, duplicate slots, lifecycle callbacks and stale timing metadata must be verified together; ordinary message retry/backoff remains a separate policy.
