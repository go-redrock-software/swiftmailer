## Design

## Implementation Plan

### Approach
Validate raw operation-specific Graph acceptance before Kiota coercion, within the existing isolated Guzzle guard and before caller/SDK retry middleware can replay a response. Keep SDK authentication/serialization/parsing/CAE and caller HTTP ownership. Use one policy per Swift send, explicit operation boundaries, permanent ambiguity latching and post-SDK acceptance checks; reentrant/new sends must have independent state. Detach any permanent refusal through the existing safe Graph failure boundary.

### Changes
Cover sendMail and draft send (202 empty response), draft/small attachment/event creation (201 with typed nonempty IDs), event update (200 with typed ID), event lookup (200 with a valid event collection; missing/malformed entries cannot mean no match), upload-session creation (201 with usable URL/expiry/initial range), and sequential upload chunks (200 progress range, 201 final Location completion). Verify statuses/fields against official current Graph contracts. Preserve documented Outlook empty-body final uploads and SDK parsing of valid models. Correct old synthetic upload fixtures that used undocumented 202 progress or omitted completion evidence, with deliberate compatibility notes. Stop malformed/incomplete/interrupted 2xx responses and post-success parsing failures permanently, including response-bearing rejected transfers, sticky middleware retries, Swift retries and pools. Keep ordinary non-success status/CAE/transient behavior unless a prior accepted notification makes replay unsafe. Audit compound operations for partial notification success before a later failure.

### Acceptance Criteria
Real GraphServiceClient/GraphRequestAdapter/Guzzle fixtures fail before fixes for each confirmed route. A malformed lookup never creates an event; incomplete draft/attachment/session/chunk results never continue or recreate drafts; ambiguous mail/event sends never report success or replay. Valid documented no-content/model/session/multi-chunk flows work, including nonseekable streams. Preserve numeric status, safe detached diagnostics, argument-recording privacy, lifecycle/failed-recipient/message restoration, envelope/policies/caller objects and separate reentrant/reset state. Exercise caller/SDK retry and Swift retry/failover/round-robin, ordinary status/network/CAE controls and focused manual mutations. Full PHP 8.3/8.5, PHPStan/style/strict Composer/generated map/aliases and exact-final-head required CI; record optional CI accurately. No dependency/vendor/baseline/threshold changes or GitLab merges.

### Risks and Sources
Stricter success/acceptance rejects previously tolerated invalid provider responses and invalid synthetic fixtures. Graph 202 means accepted for processing, not guaranteed delivery. Outlook upload completion uses a Location header and may have no JSON body; do not substitute a model-ID requirement for this documented response. Do not expose opaque upload URLs, provider bodies or SDK graphs. Keep broader Graph DSN and managed-credential work under open #30. Current Context7 SDK/contracts, official Graph operation docs and installed Kiota/LargeFileUploadTask source guide the implementation. Base is ready, unmerged !35 (`e336569e`).

### Initial proof

A real GraphServiceClient/GraphRequestAdapter/Guzzle synthetic probe on the #84/#85 branch returns HTTP 201 with `{}` for draft creation. With a large attachment forcing the draft flow, Swift_Transport_RetryTransport(maxRetries: 2) issues three POST /v1.0/me/messages requests, then reports code 0, terminal=false and retryable=true. Each earlier 201 may already have created a draft, so replay is unsafe after unconfirmed successful operation results. The failure-privacy/status changes do not resolve this separate acceptance ambiguity.

Reproduction uses Swift_GraphSdkFixture with a canned 201 JSON response, native MicrosoftGraphTransport threshold 16, a 32-byte attachment and the default retry wrapper. No real credentials/provider request or accepted delivery was used. Authoritative local evidence: /tmp/swiftmailer-86-proof.json.

Needs design: audit operation-specific success/acceptance contracts before SDK coercion across sendMail, draft creation/send, attachments/upload sessions/chunks and calendar lookup/create/update/cancel. Record known successful response status and refuse malformed/incomplete/interrupted acceptance permanently; preserve valid IDs/statuses and ordinary non-success handling. Verify no replay through SDK/caller middleware or Swift retry/pool wrappers, plus operation reset/latching, MIME/policies/events/caller ownership. Build failing-before real SDK fixtures for each confirmed route. Keep #30 open; coordinate with #84/#85 before Graph DSN construction. No GitLab merge.
