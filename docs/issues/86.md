# Issue #86: Graph acceptance ambiguity audit

**Issue:** https://code.go-redrock.com/trac/swiftmailer/-/work_items/86
**State:** workflow::needs-design

A real GraphServiceClient/GraphRequestAdapter/Guzzle synthetic probe on the #84/#85 branch returns HTTP 201 with `{}` for draft creation. With a large attachment forcing the draft flow, Swift_Transport_RetryTransport(maxRetries: 2) issues three POST /v1.0/me/messages requests, then reports code 0, terminal=false and retryable=true. Each earlier 201 may already have created a draft, so replay is unsafe after unconfirmed successful operation results. The failure-privacy/status changes do not resolve this separate acceptance ambiguity.

Reproduction uses Swift_GraphSdkFixture with a canned 201 JSON response, native MicrosoftGraphTransport threshold 16, a 32-byte attachment and the default retry wrapper. No real credentials/provider request or accepted delivery was used. Authoritative local evidence: /tmp/swiftmailer-86-proof.json.

Needs design: audit operation-specific success/acceptance contracts before SDK coercion across sendMail, draft creation/send, attachments/upload sessions/chunks and calendar lookup/create/update/cancel. Record known successful response status and refuse malformed/incomplete/interrupted acceptance permanently; preserve valid IDs/statuses and ordinary non-success handling. Verify no replay through SDK/caller middleware or Swift retry/pool wrappers, plus operation reset/latching, MIME/policies/events/caller ownership. Build failing-before real SDK fixtures for each confirmed route. Keep #30 open; coordinate with #84/#85 before Graph DSN construction. No GitLab merge.
