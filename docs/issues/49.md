# Issue #49: Sweego attachment encoding

**Branch:** fix/49-encode-sweego-attachments
**Base / review target:** !12 / fix/48-preserve-sweego-blind-recipients
**MR:** Not published
**Issue:** https://code.go-redrock.com/trac/swiftmailer/-/issues/49

## Design

### Approach
Base on !12 (`fix/48-preserve-sweego-blind-recipients`) so recipient privacy remains intact. Change only Sweego's attachment mapping: encode the helper's raw body bytes as base64 exactly once, retain required `content` and `filename` keys even for empty/zero string values, and omit only absent optional metadata. The shared helper already materializes stream bodies and will remain unchanged.

### Changes
- Sweego attachment payload construction and incorrect raw-content assertions.
- Public-send regressions for text, zero, empty, arbitrary binary and base64-looking bytes through string, in-memory stream and file-backed attachments; repeated sends verify stream readability. Include inline image IDs/dispositions and absent optional metadata.
- Provider documentation, bug-fix change note and `docs/issues/49.md`.

### Acceptance Criteria
- Demonstrate red payload probes on the old raw/truthiness mapping before changing it.
- Strict base64 decode equals the exact original bytes, required fields remain present, filename `0` survives and already-base64-looking raw data is not treated as pre-encoded.
- Inline content IDs/dispositions, MIME source, repeated sends and native To/Cc/Bcc fields are preserved.
- No shared attachment helper changes; full PHP 8.3/8.5 suites, PHPStan, full style, strict Composer validation and required CI pass.

### Risks / Limits
The transport must encode raw bodies, not the MIME wire encoding. Zero-length data encodes to an empty string and must retain its required key. Validation uses captured requests and current official sending-guide/schema contracts; no real provider email is sent. This issue does not claim the broader #47 mutation gaps are all fixed. The pending CI prerequisite fixes remain !11 and optional smoke remains #38. No merges performed.

## Implementation

### Changes

- Sweego attachment mapping now base64-encodes the raw body once, preserving required content/filename keys and filtering only absent optional disposition/content-ID metadata.
- The shared attachment reader is unchanged. It already reads and rewinds stream-backed bodies; no other provider mapping changes.
- Adds 22 public-send cases for strings, in-memory streams and file-backed bodies: text, zero/empty values, arbitrary binary, base64-looking raw bytes and content spanning read chunks. Repeated sends, original MIME, native recipient privacy, inline IDs/dispositions and absent metadata are checked. Two old raw-content assertions are corrected.
- Adds provider guidance and the bug-fix release note.

### Evidence

Sweego's [sending guide](https://learn.sweego.io/docs/sending/how_to_send_email_by_api) specifies base64 attachment content; the [send schema](https://learn.sweego.io/docs/sweego/send-send-post) marks content and filename required. Sources retrieved 2026-10-15. No real provider email was sent.

Before the source change, all 22 new cases fail against raw bytes or missing required fields. After the fix they pass (348 assertions), including strict byte-for-byte decoding, JSON encodability, filename `0`, empty/unset bodies and repeated stream/file sends. Original MIME remains unchanged; inline images retain their content ID/disposition and native Bcc privacy.

Full PHP 8.5 suite: 4,488 tests / 27,925 assertions / 30 service skips. PHP 8.3: 4,488 tests / 27,923 assertions with two existing PHPUnit E_ERROR expectation warnings and 30 service skips. PHPStan, full formatting (504 files), strict Composer validation and diff checks pass. Final-head CI results are recorded in the MR and issue after publication.
