## Design

### Approach
Base on !12 (`fix/48-preserve-sweego-blind-recipients`) so recipient privacy remains intact. Change only Sweego's attachment mapping: encode the helper's raw body bytes as base64 exactly once, retain required `content` and `filename` keys even for empty/zero string values, and omit only absent optional metadata. The shared helper already materializes stream bodies and will remain unchanged.

### Changes
- Sweego attachment payload construction and incorrect raw-content assertions.
- Public-send regressions for text, zero, empty, arbitrary binary and base64-looking bytes through string, in-memory stream and file-backed attachments; repeated sends verify stream readability. Include inline image IDs/dispositions and absent optional metadata.
- Provider documentation, bug-fix change note and `docs/issues/49.md`.

### Acceptance Criteria
- Demonstrate red payload probes on the old raw/truthiness mapping before changing it.
- Strict base64 decode equals the exact original bytes, required fields remain present, filename `0` survives and already-base64-looking raw data is not treated as pre-encoded.
- Inline content IDs/dispositions, MIME source, repeated sends and native To/Cc/Bcc fields are preserved.
- No shared attachment helper changes; full PHP 8.3/8.5 suites, PHPStan, full style, strict Composer validation and required CI pass.

### Risks / Limits
The transport must encode raw bodies, not the MIME wire encoding. Zero-length data encodes to an empty string and must retain its required key. Validation uses captured requests and current official sending-guide/schema contracts; no real provider email is sent. This issue does not claim the broader #47 mutation gaps are all fixed. The pending CI prerequisite fixes remain !11 and optional smoke remains #38. No merges performed.
