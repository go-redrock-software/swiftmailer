# Issue #103: Refuse HELO fallback when STARTTLS is required

**Branch:** fix/103-refuse-helo-fallback-with-starttls
**Issue:** https://code.go-redrock.com/trac/swiftmailer/-/work_items/103

## Design

STARTTLS is an ESMTP extension, so it cannot follow `HELO`. When STARTTLS is required and the first `EHLO` fails, throw instead of falling back to plaintext `HELO`. A required-TLS failure must also not be suppressible: listeners still receive `exceptionThrown`, but cancelling the event no longer continues the session in plaintext. The unencrypted HELO fallback and the HELO fallback after TLS stay unchanged.

## Implementation

- `Swift_Transport_EsmtpTransport::doHeloCommand()`: with STARTTLS required, a failed first `EHLO` throws `Unable to connect with STARTTLS encryption: EHLO failed: ...`. The original exception code and cause are kept.
- New private `throwRequiredStartTlsFailure()` dispatches `exceptionThrown` and then always throws. Both the EHLO path and the existing STARTTLS failure path use it. Before this change, the STARTTLS path used `throwException()`, which returns when a listener cancels the event.
- Docs: sending.md (STARTTLS flow, "best-effort" wording removed), security.md (hardening table row, TLS section), upgrading.md (BC item: stock 6.x had the same fallback), CHANGES.
